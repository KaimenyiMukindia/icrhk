# Event Creation, Listing, and Front-End Dynamic Display Fixes

## Summary of the Issues
The project had three major logic problems in the event flow:

1. The save handler did not reliably insert the event into the `evt_events` table, so the admin list and front-end registration page had no source data to render.
2. Empty slug values were treated as a validation error instead of generating a safe unique slug from the event title.
3. The front-end registration page relied on event data that was not being saved or retrieved consistently, which prevented dynamic display of event information, tickets, speakers, and sponsorship cards.

## Root Cause and Fixes
### Event save path
The event form was writing values into the event table, but the payload shape and field mapping did not match the actual schema in a stable way. The main fix was to ensure the event insert/update logic writes the values in the correct order and includes the required fields expected by the database.

The event save flow now:

- accepts the title, description, date, venue, status, and nested ticket/speaker/sponsor data;
- generates a unique slug automatically if the slug is empty or duplicate;
- writes the saved event record to `evt_events` with its related data linked through `event_id` in the child tables;
- keeps the AJAX registration flow intact without breaking the existing success/error response contract.

### Slug generation and migration
Older database installations may still be missing the `slug` column or unique key on `evt_events`. The system now checks for that schema on admin load and adds the missing `slug` field and index if necessary.

The slug generation is handled defensively:

- the slug is built from the event title with `sanitize_title()`;
- if the title is empty, the system falls back to `event`;
- if the slug already exists, a numeric suffix is added until the value becomes unique;
- the form does not block save if the slug field is blank because it will be generated on the server side.

### All Events list
The list page reads from `evt_events` and displays the event names, dates, venue, status, and counts. The query was aligned with the real table structure so it displays saved events correctly and includes status filtering and aggregated registration totals.

### Front-end dynamic display
The front-end template now accepts either:

- `?event_id=123`
- `?event_slug=my-event`

The page fetches the matching event and then loads the related ticket types, speakers, and sponsorship packages from their custom tables. If no event is specified, it defaults to the most recent published event so the page still has meaningful content.

## Event URL Structure
The front-end event registration pages can be reached with unique event URLs such as:

- `/register?event_id=123`
- `/register?event_slug=my-event`

This gives each event a stable and unique registration path while enabling multiple events to coexist simultaneously in the same site.

## Administrator Workflow
To create and publish a working event:

1. Open the admin menu for the plugin and click “Add New Event.”
2. Enter the event title, date, venue, and description.
3. Leave the slug blank if you want it autogenerated, or enter a custom slug manually.
4. Add ticket types, speaker profiles, and sponsor packages for the event.
5. Set the status to “Published” when the event is ready to go live.
6. Save the event and return to the “All Events” list.
7. Confirm the new event appears in the list with the correct data.
8. Open the front-end page using the event-specific URL, such as `/register?event_slug=my-event`.
9. Confirm the hero, conference details, speakers, sponsorship section, and registration form display the saved data.

## Admin UI panel split and default-state fix
The event creation admin form was also refined to match the workflow expectations for event setup:

- the first panel was renamed to “Basic Event Info” and kept as the primary editable section;
- the marketing and front-end display fields were moved into a second panel named “Event Display & Marketing Content”;
- the front-end visibility toggle for the event information block was relocated to the marketing panel header;
- the accordion logic now keeps the first panel open while all later panels start collapsed unless the user expands them.

This keeps the core event setup visible and organized without hiding optional display content behind the default open state.

## Result
The plugin is now able to:

- create and save multiple distinct events;
- auto-generate unique slugs without errors;
- show all saved events in the admin list;
- render event-specific content on the front end;
- save registrations for the correct event and ticket type;
- show the event and ticket association in the admin registrations list;
- present a clearer create/edit event UI with the requested split and default panel behavior.

The only remaining missing piece remains payment processing, which is intentionally out of scope for this task.
